# v0.3.0 Onboarding Input Repair

## Observed behavior

`scanBlueBoard.ps1` and `diagnosePedalboard.ps1` discover the iRig BlueBoard,
but `onboardPedalboard.ps1` can fail before (or while) presenting a numbered
selection. This is not a BLE pairing failure: all three commands use the same
read-only BlueBoard discovery implementation.

## Root cause

The initial launcher exposed only environment options and relied on PowerShell's
automatic `$args` collection for every `onboard` option. The Python workflow
allows numbered choices only when both standard input and output are a terminal.
When PowerShell or its host does not provide that terminal contract, onboarding
correctly rejects the interactive input path. The diagnostic command has no
numbered setup prompts, so it continued to find the same hardware.

## Repair

1. Expose the onboarding device and profile fields as native PowerShell
   parameters and translate them directly to the CLI.
2. If the local profile already exists, make the launcher perform a fresh,
   read-only `--verify-existing` check by default. This uses the saved profile
   and never asks for setup selections or writes a file.
3. Require `-Force` for intentional replacement. In non-interactive mode,
   require the existing explicit CLI safety acknowledgements.
4. Keep a clear CLI error for genuinely non-interactive first-run sessions.

## Acceptance checks

- `./onboardPedalboard.ps1` with a saved profile reaches the same readiness
  path as `./diagnosePedalboard.ps1`, without a prompt or local write.
- `./onboardPedalboard.ps1 -Force` enters deliberate reconfiguration.
- `./onboardPedalboard.ps1 -NonInteractive -Model katana100 -Layout panel-first
  -Output "KATANA 1" -Address "..." -AcceptProfileStateDefaults -Force` can
  configure without terminal input.
- The workflow never opens a MIDI output or sends MIDI in any of these paths.
