# v0.3.0 Unified Windows Onboarding and Reliability Release

## Summary

- Replace the three-command Windows first-run path with one safe onboarding
  launcher while retaining the existing setup, configure, and doctor tools.
- Install dependencies before invoking package code, then run independent MIDI
  and BLE discovery concurrently and reuse their typed results.
- Keep onboarding read-only with respect to the amplifier and operating system:
  it never opens a Katana output, sends MIDI, or executes configured actions.
- Keep the release focused on Windows onboarding and reliability. Expression
  control, SysEx, authoritative state, persistent state LEDs, and Linux onboarding
  parity remain deferred.

## Implementation changes

- Add `onboardPedalboard.ps1`. It reuses a compatible `python/.venv`, invokes
  `setupPedalboard.ps1` when the environment is absent, incompatible, stale, or
  explicitly refreshed, and then runs `blueboard-katana onboard`.
- Add an `onboard` CLI command with the same profile and discovery options as
  `configure`.
- Add a focused onboarding module with:
  - a typed `DiscoverySnapshot` containing Python, MIDI, BLE, and existing-config
    inspection results;
  - concurrent MIDI enumeration and BlueBoard scanning;
  - a typed `ReadinessReport` shared by onboarding and standalone doctor;
  - interactive retry of only failed discovery sources;
  - configuration validation and readiness evaluation before any local write.
- Keep standalone `doctor` fresh: it collects a new snapshot every time. Keep
  standalone `configure` and all specialist scripts available for troubleshooting.
- Preserve cancellation, timestamped backups, atomic configuration replacement,
  last-address persistence, dry-run defaults, and explicit action enablement.
- Move version declarations to `0.3.0` while retaining the alpha classifier.

## Public interfaces

```text
.\onboardPedalboard.ps1 [-PythonExe PATH] [-Dev] [-RefreshEnvironment]
  [-Output NAME] [-Model MODEL] [-Layout LAYOUT] [-MidiChannel N]
  [-Firmware VERSION] [-Name SUBSTRING] [-Address ADDRESS] [-ScanTimeout SECONDS]
  [-NonInteractive] [-AcceptProfileStateDefaults] [-Force] [-VerifyExisting]

blueboard-katana onboard --config PATH
  [--output NAME] [--model MODEL] [--layout LAYOUT]
  [--midi-channel N] [--firmware VERSION]
  [--name SUBSTRING] [--address ADDRESS] [--scan-timeout SECONDS]
  [--state-file PATH] [--non-interactive]
  [--accept-profile-state-defaults] [--force] [--verify-existing]
```

Exit code `0` means ready, `2` means a configuration or readiness problem, and
`130` means the user interrupted the workflow. The JSON configuration schema is
unchanged.

## Onboarding input repair

- [x] Expose onboarding profile and discovery controls as native PowerShell
  parameters instead of depending on the automatic `$args` collection.
- [x] When a local profile already exists, default the launcher to a fresh,
  read-only `--verify-existing` readiness check; use `-Force` for intentional
  replacement.
- [x] Keep terminal-driven numbered choices for a real interactive terminal and
  make the non-interactive CLI diagnostic explain the required explicit flags.
- [x] Test that saved-profile verification performs exactly one fresh MIDI/BLE
  discovery cycle without prompting, opening a MIDI port, sending MIDI, or
  changing the configuration.
- [x] Use a 20-second default BLE diagnostic window in onboarding and generated
  profiles, and apply it to the standalone scan and doctor PowerShell helpers.
- [ ] The Windows launcher discovers `KATANA 1` and the intended BlueBoard once,
      writes the expected Panel-first profile, and reports READY without changing
      the amplifier.
- [ ] The generated profile completes an A-D dry run before actions are enabled.
- [ ] `v0.3.0` is tagged only after automated validation and the Windows hardware
      onboarding smoke test pass.

Reconnect, endurance, Linux hardware qualification, expression input, SysEx, and
authoritative amplifier state remain later release gates unless separately
validated and recorded.

## Assumptions

- Unified means one user-facing command, not running configuration before its
  required environment exists.
- Windows is the only new onboarding target in v0.3.0.
- Existing standalone scripts remain supported and are not deprecated.
- A successful source-level check never substitutes for a physical amplifier
  observation.
