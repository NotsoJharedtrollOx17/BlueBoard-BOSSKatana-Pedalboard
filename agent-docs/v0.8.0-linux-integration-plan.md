# v0.8.0 Linux BlueBoard–Katana Integration Plan

## Objective and release boundary

Port the physically proven Windows BlueBoard-to-original-KATANA-100 Mk I
workflow to Linux Mint 22.2 x86-64 without expanding the amplifier protocol or
turning this repository back into a general macro handler. The Windows behavior
remains the regression baseline. Version 0.8.0 remains alpha and is not release
complete until both automated validation and the separate live Linux acceptance
record pass.

The implementation starts from the checked-out `dev` v0.7.0 runtime. No branch
reconciliation is part of this work. The pre-existing untracked
`V0.8.0_LINUX_PORT_ANALYSIS.md` is user-owned evidence and must remain unchanged.

## Product boundary

- Retain the `blueboard_macro_handler` package namespace for import and command
  compatibility.
- Accept only `katana`, harmless `log`, or `null` binding actions.
- Reject `keyboard`, `udp`, `launch`, and legacy macro aliases during
  configuration loading with migration guidance.
- Delete the Linux and Windows keyboard backends and remove `evdev`, `uinput`,
  UDP, and process-launch setup/runtime paths.
- Keep dry-run as the default. `--execute-actions` enables Katana actions only.
- Keep momentary `--led-feedback` independent from Katana actions and dry-run.
- Retain only `katana` and `dev` optional dependency groups.

## BLE and BlueZ transport

Bleak over BlueZ/D-Bus is primary. The compatibility path is activated only when
BlueZ connects but omits the advertised BLE-MIDI service. It uses an immutable
internal `BlueBoardGattProfile` containing the profile name, MIDI value handle,
CCCD handle, and discovery source.

Compatibility discovery proceeds fail-closed:

1. Run `gatttool --characteristics` and require exactly one BLE-MIDI
   characteristic UUID.
2. Bound that characteristic's descriptor span by the next declaration and run
   `gatttool --char-desc` inside that span.
3. Require exactly one `0x2902` client-configuration descriptor.
4. Use those handles for notifications and outbound LED packets.
5. If validated discovery fails, allow `0x0022`/`0x0023` only when the advertised
   name equals `iRig BlueBoard` case-insensitively.
6. Refuse unknown devices, missing tools, invalid spans, malformed output,
   missing or duplicate characteristics, and missing or duplicate CCCDs.

Connection logs record backend, profile, value handle, CCCD handle, and whether
the source was discovered or name-bound. The application never pairs, trusts,
or changes persistent BlueZ device state.

## ALSA selectors and Linux interaction model

Input and output names remain separate configuration fields and are derived
independently. Starting from the exact selected enumerated name, Linux onboarding
may remove a trailing ALSA `client:port` token and then a redundant client prefix
before `:`. It saves the shortest candidate that still resolves uniquely to the
original selected port. Ambiguity preserves the longer name.

The Linux entry points are:

- `setupPedalboard.sh`: APT-family prerequisite checks, optional system-package
  installation, Python 3.10-3.12 selection, venv creation, and `.[katana]` or
  `.[katana,dev]` installation. It supports `--skip-system`, `--dev`, and
  `--python-exe`; it never touches `uinput` or group membership.
- `onboardPedalboard.sh`: compatible v0.8.0 environment reuse or refresh,
  profile creation/replacement/verification, full model/layout/port/firmware
  options, and exact exit-status forwarding.
- `diagnosePedalboard.sh`: fresh read-only readiness checks.
- `recordPedalboardSession.sh`: timestamped JSONL evidence, dry-run by default,
  explicit `--active`, optional duration, device/debug/LED overrides, signal
  forwarding, and child exit-status preservation.

Doctor enumerates but never opens MIDI ports. It reports Linux distribution and
support class, kernel, architecture, BlueZ version/service/D-Bus/adapter,
`gatttool`, ALSA sequencer, Mido/RtMidi versions and APIs, saved and resolved
input/output selectors, configured model/firmware, all production-approved
effect definitions, and current BlueBoard scan results. Linux port-open failures
point to common ownership and ALSA-access causes. The runtime retains input-first
duplex opening, connection-epoch invalidation, bounded recovery, and state
resynchronization.

## Automated gates

The automated gate includes:

- all Katana protocol, synchronization, recovery, late-reply, timeout, LED,
  shutdown, and dry-run regressions;
- removed-action rejection and absent macro module/dependency assertions;
- ALSA coordinate drift, prefix removal, ambiguity, missing-port, exact-name,
  and independent-direction fixtures;
- alternate GATT handle layouts, validated discovery, named fallback, unknown
  device refusal, malformed/missing/duplicate descriptors, active-handle LED
  writes, process loss, reconnect, and cleanup fixtures;
- Bash forwarding, dry-run, JSONL name, signal, and exit-status tests;
- Windows and Ubuntu Python 3.10/3.12 jobs installing `.[katana,dev]`;
- wheel and sdist installation/smoke on clean Windows and Ubuntu environments;
- unit tests, Ruff, PowerShell parsing, `bash -n`, package smoke, and
  `git diff --check`.

## Live Linux release gate

Use Linux Mint 22.2 x86-64, the original KATANA-100 Mk I at firmware 4.00, and
the BlueBoard powered in mode 2 by holding C. Select the actual Mido input and
output ports independently. Record sanitized OS/kernel/BlueZ/backend/port/profile
evidence, then verify startup reads, A/B post-PC synchronization, C/D first-press
pre-read and post-CC verification, A-D BLE and momentary LEDs, BlueBoard
power-cycle reconnect, Katana unplug/replug recovery, unknown state after failed
reads, Ctrl+C cleanup, a bounded 60-minute active session, and selector recovery
after a user-controlled reboot.

Do not merge to `main`, tag v0.8.0, or describe the release as complete while
any live gate is unchecked.

## Explicitly out of scope

- C++ port, daemon, boot service, or automatic startup;
- Linux qualification for Mk II;
- persistent Katana-state LED display;
- arbitrary SysEx addresses or a general SysEx write surface;
- pairing/trusting BlueBoard state;
- broad non-APT Linux distribution support.
