# BlueBoard–BOSS Katana Pedalboard v0.8.0 Linux Port Analysis

Status: source audit and implementation proposal, 2026-08-31  
Target: original BOSS KATANA-100 Mk I, exact supported firmware 4.00, Linux Mint/Ubuntu x86-64 desktop session  
Repository reviewed: [`BlueBoard-BOSSKatana-Pedalboard`](https://github.com/NotsoJharedtrollOx17/BlueBoard-BOSSKatana-Pedalboard)

## Executive decision

The proposed roadmap is sufficient, with one mandatory prerequisite and two refinements.

1. **Reconcile the branch before implementing v0.8.0.** The remote `dev` branch currently resolves to `fc9e1412cc13fe778639524cd5e395ac8d858d5e`, which is also tag `v0.6.0`. The newer `v0.7.0` tag resolves to `a1613d504ca2fe4768d9390f38f44180c4ab3524` and is two commits ahead. The synchronization runtime described in the roadmap is in the tag, not in the current remote `dev` branch. The clean starting operation is a fast-forward of `dev` to the tagged v0.7.0 commit.
2. **Treat ALSA names as selectors, not durable device identities.** The existing resolver already supports exact, case-insensitive, and unique-substring matching independently for input and output. Linux onboarding should save the shortest selector that remains unique in each direction instead of persisting a client-number-bearing enumeration string.
3. **Make fixed BlueBoard ATT handles an explicit compatibility profile.** Normal Linux operation should remain Bleak over BlueZ/D-Bus. The `gatttool` fallback may remain for v0.8.0, but handles `0x0022` and `0x0023` must be discovered or tied to a named, physically verified BlueBoard profile. They must not be presented as universal Linux facts.

This is therefore a Linux productization and hardware-qualification release, not a rewrite or a new runtime port.

## What is already portable

The maintained runtime is already divided at appropriate boundaries:

```text
BlueBoardClient
    -> BleMidiDecoder
    -> Router
    -> ActionDispatcher
    -> KatanaRuntime worker
    -> KatanaSysExSession
    -> MidoMidiTransport
    -> operating-system MIDI backend
```

The following components require no Linux rewrite:

- BLE-MIDI packet decoding, normalization, and routing.
- Press/release edge handling, duplicate suppression, cooldowns, and dry-run safety.
- Roland SysEx framing, checksum validation, address/length matching, timeouts, retries, and late-reply rejection.
- The six firmware-scoped Mk I 4.00 effect reads.
- Authoritative startup, post-Program-Change, pre-toggle, and post-Control-Change state synchronization.
- The single-worker Katana command order and connection-epoch recovery model.
- Independent MIDI input and output abstractions.
- Unknown/stale/predicted/queried state provenance and failure invalidation.
- Structured logging, metrics, bounded runtime duration, and orderly resource shutdown.

Bleak's Linux backend communicates with BlueZ over D-Bus, so the normal BLE path already uses the intended Linux stack. Mido's recommended RtMidi backend is a wrapper around `python-rtmidi`; on Linux it exposes ALSA sequencer ports whose names can include client and port identifiers. ALSA itself models routing as changing clients and ports, which is why persisted numeric identities should be avoided.

References: [Bleak Linux backend](https://bleak.readthedocs.io/en/latest/backends/linux.html), [Mido RtMidi backend](https://mido.readthedocs.io/en/latest/backends/rtmidi.html), [ALSA sequencer interface](https://www.alsa-project.org/alsa-doc/alsa-lib/seq.html).

## Recommended implementation sequence

### PR 0 — Establish the real v0.8.0 base

- Fast-forward `dev` from `fc9e141` to `a1613d5`.
- Update the v0.7.0 acceptance record with the completed Windows observations: startup reads, post-PC sync, pre-toggle read, post-CC readback, first-press behavior, reconnect behavior, and cleanup.
- Add a v0.8.0 feature plan that names one target OS image and kernel/hardware environment.
- Change package development status only at release time, after physical Linux acceptance.

Exit gate: the checked-out `dev` branch contains `katana/runtime.py`, reports version 0.7.0, and the recorded Windows evidence matches the current project status.

### PR 1 — Linux installation and wrapper parity

Add:

```text
onboardPedalboard.sh
diagnosePedalboard.sh
recordPedalboardSession.sh
```

Modify `setupPedalboard.sh`:

- Default to `.[katana]` rather than `.[katana,linux]`.
- Add an explicit `--with-keyboard-actions` option that includes `evdev` and runs `/dev/uinput` checks.
- Keep `--skip-system` and `--dev` behavior.
- Detect a supported Python interpreter and `venv` support before attempting environment creation.
- Check for BlueZ tools/service availability and ALSA runtime availability; explain missing packages before optional installation.
- Keep `apt-get` explicit and skippable. Do not silently broaden support to non-APT distributions.
- Do not modify group membership unless the user opts into keyboard actions. Print logout/login guidance only if this invocation actually changed membership.

The new onboarding wrapper should mirror `onboardPedalboard.ps1`: validate or refresh the expected v0.8.0 environment, preserve `--verify-existing` and `--force` semantics, forward input/output/model/layout/firmware/device options, and exit with the Python command's status.

The session wrapper should preserve:

- dry run by default;
- an explicit `--active` flag for MIDI and configured actions;
- optional bounded duration;
- JSON Lines output in a timestamped log;
- debug, LED, address, name, and scan-timeout forwarding;
- Ctrl+C propagation and cleanup;
- the exact runtime exit status.

All new project-owned shell variables and functions should use camelCase.

Exit gate: a clean Mint/Ubuntu user can set up the Katana-only profile without root after optional system packages are present, run onboarding, run the doctor, and record a bounded dry-run session.

### PR 2 — Stable ALSA MIDI selection

Preserve the current separate `inputName` and `outputName` fields. Do not collapse them into one Katana port value.

Add a conservative helper around the existing resolver:

```python
def deriveStablePortSelector(
    selectedName: str,
    availableNames: tuple[str, ...],
) -> str:
    ...
```

Its contract should be:

1. Return the exact name when no shorter safe selector exists.
2. On Linux, try removing only recognized trailing ALSA client/port tokens such as `128:0`.
3. Accept the shortened value only if `resolveInputName` or `resolveOutputName`, as applicable, still resolves to exactly one current port.
4. Never guess when two ports share the same shortened name.
5. Show both the current enumerated name and saved selector during onboarding.

This retains backward compatibility and allows a persisted selector such as `KATANA MIDI 1` to survive ALSA client-number drift. Input and output must be tested independently even when the displayed strings happen to be equal.

Add fixtures covering at least:

```text
KATANA MIDI 1 20:0
KATANA MIDI 1 24:0
KATANA:KATANA MIDI 1 20:0
20:KATANA MIDI 1 0
```

Also cover an exact match, a case-insensitive match, one unique substring, no match, ambiguous input, ambiguous output, and different input/output lists.

Open the input before the output exactly as the v0.7.0 session does. Confirm on hardware that this order permits full-duplex SysEx. Do not add a Linux-specific transport unless Mido/RtMidi fails physical qualification.

Exit gate: reconnect and reboot do not break a saved profile solely because ALSA assigned a different numeric client identifier.

### PR 3 — BlueZ compatibility hardening

Keep Bleak as the primary implementation. The normal path should discover the standard BLE-MIDI service and characteristic by UUID and subscribe through BlueZ/D-Bus.

Replace the two module-global fixed handles with an explicit type:

```python
@dataclass(frozen=True)
class BlueBoardGattProfile:
    name: str
    midiValueHandle: str
    midiCccHandle: str
```

Recommended fallback order:

1. Bleak UUID discovery and notification subscription.
2. `gatttool` characteristic/descriptor discovery, with parsed handles validated against the BLE-MIDI characteristic UUID.
3. A named fixed-handle profile only for the exact BlueBoard hardware/firmware combination physically verified in acceptance.
4. Fail closed with a diagnostic message if no compatible profile or valid discovery result exists.

Do not silently use `0x0022`/`0x0023` for an unknown device. Log the selected backend, profile, discovered characteristic handle, CCCD handle, and whether the values were discovered or profile-bound. Do not log unrelated device data.

Add parser fixtures for successful discovery, missing characteristic, missing CCCD, duplicate characteristic, malformed output, connection loss, and a handle layout different from `0x0022`/`0x0023`.

Exit gate: normal Bleak operation and the intended compatibility path both reconnect as a normal desktop user, and a BlueBoard reconnect never tears down the Katana runtime.

### PR 4 — Linux diagnostics and operational parity

Extend the existing read-only `doctor` flow. It should continue to enumerate MIDI and scan BLE without opening Katana MIDI ports or sending messages.

Recommended Linux checks:

| Check | Result should report |
|---|---|
| Python | interpreter, supported version range, venv path |
| Distribution | `/etc/os-release` identity and supported/best-effort classification |
| BlueZ | tool availability, service state, adapter presence |
| D-Bus | whether the session can reach the BlueZ object manager |
| Bleak | backend import and BlueZ version requirement message |
| Mido/RtMidi | backend import and input/output enumeration |
| ALSA | independent configured selector resolution |
| Keyboard actions | only when configured; `evdev`, `/dev/uinput`, and permission status |
| Configuration | exact Mk I model, firmware, state-sync settings, six production definitions |

Port ownership is different from enumeration. A read-only doctor cannot promise that a port is openable without opening it. Report this distinction and, when active startup later receives a busy/access error, add Linux-specific guidance to close Tone Studio, DAWs, MIDI monitors, or stale pedalboard processes.

Keep diagnostics structured enough to attach to an issue. JSON logs should include platform, Python version, selected BLE backend, resolved ALSA input/output names, and stop reason, while avoiding secrets and unrelated Bluetooth inventory.

Exit gate: one diagnostic run distinguishes missing package, stopped BlueZ, inaccessible D-Bus, absent adapter, absent Katana, ambiguous ALSA selector, missing BlueBoard, and active port failure.

### PR 5 — Linux CI and packaging gates

Change Ubuntu test jobs to install at least `.[katana,dev]`. Do not require `evdev` for core Katana CI.

Add:

- Runtime import tests asserting that normal Linux execution does not import `blueboard_macro_handler.actions.windows`.
- Tests for the ordinary Bleak path and the BlueZ compatibility path.
- ALSA-shaped resolver and stable-selector fixtures.
- Existing duplex SysEx recovery, late-reply rejection, connection-epoch invalidation, and clean-shutdown tests under Ubuntu.
- A Linux package-smoke job that builds both wheel and sdist, creates clean environments, installs each artifact with Katana dependencies, invokes the console entry point, validates the example configuration, and runs non-hardware list/help commands.
- Shell behavior tests for argument forwarding and exit-code preservation, in addition to `bash -n`.

The current `testPackageActions.py` imports the Windows module directly as a unit-test target. That test may remain, but it is not evidence that Linux runtime imports are safe. Add a separate fresh-process import test against the actual Linux entry point.

Exit gate: Windows and Ubuntu remain green on Python 3.10 and 3.12; Linux package installation is proven from both distribution formats; the Linux runtime import graph is platform-safe.

### PR 6 — Physical Linux acceptance

Run acceptance on the exact machine that defines support. Record:

- distribution and version;
- kernel version;
- BlueZ version;
- Python version;
- `mido` and `python-rtmidi` versions;
- Katana model and firmware;
- BlueBoard hardware/firmware identity if available;
- enumerated and saved MIDI input/output names;
- selected BLE backend and compatibility profile;
- bounded session duration and final metrics.

Required sequence:

1. Startup reads all six physical effect flags correctly.
2. A and B change Tone Settings and trigger post-PC synchronization.
3. C and D work on their first press from the authoritative startup state.
4. Logs show the pre-toggle read and post-CC readback.
5. BlueBoard disconnect/reconnect does not restart the Katana runtime.
6. Katana unplug invalidates state; replug recovers both ports and resynchronizes.
7. Timeout, malformed reply, or reconnect failure leaves state unknown rather than false.
8. Ctrl+C closes BLE plus both ALSA MIDI ports.
9. A bounded rehearsal-duration active session completes without leaked resources or silent state drift.
10. The same profile is rechecked after reboot to expose ALSA client-number instability.

Exit gate: all ten items have attached log evidence and no unresolved blocker is relabeled as best-effort support.

## Release boundary

Recommended v0.8.0 definition:

> Feature parity for the original BOSS KATANA-100 Mk I firmware 4.00 on Windows and one physically validated Linux Mint/Ubuntu x86-64 desktop target, including authoritative startup, post-PC, pre-toggle, and post-CC SysEx synchronization; independent full-duplex MIDI ports; BlueBoard reconnection; structured bounded sessions; and clean shutdown.

Explicit exclusions:

- support claims for every Linux distribution or architecture;
- a system daemon, service unit, or automatic startup at boot;
- Mk II support;
- persistent amplifier-state BlueBoard LEDs;
- Tone Studio or DAW coexistence guarantees;
- continuous polling;
- arbitrary SysEx reads or writes;
- automatic system-package installation without an explicit setup option;
- `/dev/uinput` as a requirement for Katana-only operation.

## Final recommendation

Proceed with the roadmap as v0.8.0, but start from v0.7.0 rather than the current remote `dev` tip. The smallest credible implementation is six focused PRs after that branch reconciliation: Linux wrappers/setup, ALSA selector stability, BlueZ compatibility profiles, diagnostics/session parity, Linux CI/package smoke, and physical qualification.

The core synchronization design should be frozen during this work unless physical Linux testing exposes a transport-level defect. That keeps the release focused on making the already-correct runtime installable, diagnosable, repeatable, and supportable on one real Linux target.
