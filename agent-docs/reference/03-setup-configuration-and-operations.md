# Setup, configuration, and operations

## Supported environment

- Python 3.10, 3.11, or 3.12.
- iRig BlueBoard in the validated mode 2 profile: hold C while powering on.
- Original BOSS KATANA-100 MkI for the qualified profile; connect with a USB data
  cable and use original-generation BOSS Tone Studio.
- Windows with the model-correct BOSS USB driver, or Linux Mint 22.2 x86-64 with
  BlueZ, ALSA sequencer support, Mido, and python-rtmidi.

Python 3.13+ is not a supported release path because the pinned runtime range is
designed around readily installable python-rtmidi wheels through Python 3.12.
Check the official BOSS support page for current model-specific firmware,
drivers, and applications rather than copying a MkII version onto a MkI.

## Safety before first connection

1. Back up important Tone Settings.
2. Set a safe amplifier output volume.
3. Identify the exact amplifier generation and firmware.
4. Close Tone Studio, DAWs, MIDI monitors, and stale bridge processes before a
   live port test.
5. Start with onboarding/doctor, then dry-run, then intentional active control.
6. Stop on an unexpected amplifier state, ambiguous port, invalid SysEx frame,
   unbounded reconnect loop, or failed restoration.

## Normal Windows workflow

From PowerShell at the repository root:

```powershell
.\onboardPedalboard.ps1
.\runPedalboard.ps1 --debug
.\runPedalboard.ps1 --debug --execute-actions
```

`onboardPedalboard.ps1` reuses a compatible environment or performs setup,
discovers BlueBoard and Katana ports, guides model/layout selection, displays the
complete A-D mapping, and writes the ignored local profile only after
confirmation. Running it again verifies the saved profile. Use `-Force` only for
an intentional replacement; the old local file is backed up first.

For repeatable original-MkI setup, use the exact names enumerated on that host:

```powershell
.\onboardPedalboard.ps1 -NonInteractive -Model katana100 `
  -Layout panel-first -Input "KATANA 0" -Output "KATANA 1" `
  -Firmware "4.00" -AcceptProfileStateDefaults -Force
```

The observed Windows machine used `KATANA 0` for input and `KATANA 1` for output.
Port numbering is host-specific; enumerate instead of hard-coding these names.

Specialist tools remain available:

```powershell
.\setupPedalboard.ps1
.\listKatanaMidiInputs.ps1
.\listKatanaMidiOutputs.ps1
.\configurePedalboard.ps1
.\diagnosePedalboard.ps1
.\scanBlueBoard.ps1
```

If script policy blocks a helper, use a process-scoped bypass rather than
changing the machine-wide policy.

## Normal Linux workflow

On the supported Linux Mint target:

```bash
./setupPedalboard.sh --dev
./onboardPedalboard.sh
./diagnosePedalboard.sh
./runPedalboard.sh --debug
./runPedalboard.sh --debug --execute-actions
```

Setup installs the Katana optional dependencies and uses Python 3.10-3.12. Use
`--skip-system` only after installing the required BlueZ, venv, and ALSA packages.
The script does not configure `uinput`, change groups, pair devices, or trust
Bluetooth devices.

Linux onboarding enumerates input and output separately. It may remove unstable
ALSA `client:port` coordinates or a redundant client prefix only when the shorter
selector still resolves uniquely to the same full port. Verify saved selectors
after reconnects or reboot:

```bash
./onboardPedalboard.sh --verify-existing
```

## What onboarding and doctor may do

Onboarding and doctor may:

- inspect Python and installed packages;
- enumerate MIDI input and output names without opening them;
- scan for the BlueBoard;
- inspect read-only OS/BlueZ/ALSA readiness;
- validate configuration and production-approved definitions;
- write a user-confirmed local profile and timestamped backup during onboarding.

They may not open the Katana port, send MIDI, execute an operating-system action,
pair/trust the BlueBoard, or silently choose among ambiguous devices. Doctor
returns 0 when ready and 2 for an actionable readiness failure.

## Configuration files

| File | Meaning |
|---|---|
| `python/config/blueboard.json` | Safe committed default; A-D are unmapped |
| `python/config/katana-pedalboard.example.json` | General editable reference |
| `python/config/katana-pedalboard-panel.example.json` | Original-MkI Panel-first template |
| `python/config/katana-pedalboard.local.json` | Ignored machine-specific profile generated by onboarding |

The committed Panel example intentionally uses placeholder hardware data,
including firmware `unknown`; it does not become an exact-firmware synchronized
profile until onboarding records the real firmware and independent port names.

## Configuration model

`device` contains the BlueBoard name, scan timeout, and `pair=false`. Persistent
pairing is rejected.

`katana` contains:

- independent `inputName` and `outputName` selectors;
- JSON MIDI channel 1-16, converted to wire channel 0-15;
- model `katana100` or `katana100MkII`;
- firmware evidence and Roland device ID;
- optional `stateSync` timeout/retry settings;
- model-correct effect CC assignments; and
- short-lived per-preset predictions used around Program Change.

Each binding contains BlueBoard CC, channel, edge, optional cooldown, and one
legal action. `selectPreset`, `setEffectState`, and `toggleEffect` are the Katana
commands. Validate an edited file offline:

```powershell
.\python\.venv\Scripts\python.exe -m blueboard_macro_handler validate `
  --config .\python\config\katana-pedalboard.example.json
```

## Command surface

| Command | Side effects and use |
|---|---|
| `scan` | BLE discovery only |
| `onboard` | Discover, confirm, write/verify local config; never sends MIDI |
| `configure` | Specialist guided config generation; never sends MIDI |
| `doctor` | Fresh read-only readiness checks |
| `validate` | Offline config normalization |
| `replay` | Offline BLE-MIDI fixture routing |
| `midi-inputs` / `midi-outputs` | Enumerate without opening ports |
| `run` | Dry-run by default; `--execute-actions` enables Katana sends |
| `katana-test` | Sends exactly one explicit standard-MIDI diagnostic message |
| `probe-effects` | Sends bounded documented PC/CC messages after typed consent |
| `sysex-probe` | Sends predefined bounded RQ1 reads after typed consent; optional fixture save has a second confirmation |
| `init-config` | Writes an editable harmless default |

Always inspect `blueboard-katana COMMAND --help` for the executable interface.

## Dry-run, active control, and LEDs

```powershell
.\runPedalboard.ps1 --debug
.\runPedalboard.ps1 --debug --execute-actions
.\runPedalboard.ps1 --debug --execute-actions --led-feedback
```

Dry-run connects and routes but does not send configured Katana actions. LED
feedback is independent: it can be tested in dry-run, and enabling it does not
enable Katana actions. LEDs are momentary button acknowledgement, not persistent
amplifier-state indicators.

Before active use, confirm logs show channel-1 CC20-CC23 press/release events and
the intended A-D mapping. In synchronized MkI mode, confirm startup produces six
queried flags; if synchronization fails, preset actions can remain usable but
relative toggles should be rejected as unknown.

## Bounded session evidence

Windows:

```powershell
.\recordPedalboardSession.ps1 -DurationMinutes 5
.\recordPedalboardSession.ps1 -Active -LedFeedback -DurationMinutes 60
```

Linux:

```bash
./recordPedalboardSession.sh --debug --led-feedback --duration-minutes 5
./recordPedalboardSession.sh --active --debug --led-feedback --duration-minutes 60
```

Recorders write ignored timestamped JSONL. They are dry-run unless `-Active` or
`--active` is supplied. Preserve the final metrics and stop reason, then sanitize
Bluetooth addresses, host/user paths, serial numbers, and unrelated device data
before attaching evidence.

## Read-only SysEx probe

Run probes only after enumerating both directions and closing competing clients.
On the observed Windows host:

```powershell
.\probeKatanaSysEx.ps1 --model katana100 `
  --input "KATANA 0" --output "KATANA 1" --read effect-states --debug
```

The predefined targets are `current-selection`, `effect-states`, and
`panel-snapshot`. The command requires `READ` before port open. Fixture output
requires a separate `SAVE`. A target succeeds only if every required response is
checksum-valid, address-matched, correctly sized, and decodable within bounded
timeouts/retries. Diagnostic reads do not update a separately running controller.

## Standard-MIDI probe

`katana-test` sends one explicit PC or CC. `probe-effects` uses only the
documented controls for the selected model, requires `PROBE`, prompts for a
physical observation after on/off, and attempts to turn the current switch off
on interruption. It does not scan unknown controllers or send SysEx.

## Common troubleshooting

| Symptom | Check |
|---|---|
| Tone Studio reports `WRONG DEVICE` | Confirm original MkI versus MkII and install the matching Tone Studio family |
| Input/output missing or ambiguous | Close competing MIDI clients; enumerate both directions and use exact or unique selectors |
| MkI CC19 appears ineffective | CC19 is Send/Return; an inactive effects loop may have no audible result |
| D controls the wrong effect | MkI Delay/FX is grouped CC17; do not apply MkII's independent map |
| Toggle rejected as unknown | Confirm firmware 4.00, `stateSync`, both ports, six approved definitions, and successful reads |
| Linux service omitted after BLE connect | Confirm full BlueZ plus `gatttool`; inspect backend/profile logs; do not broaden the named fallback |
| ALSA port breaks after reboot | Run `--verify-existing`; preserve a longer selector if shortening is ambiguous |
| Windows test suite stalls in Linux fallback test | Ensure the test patches `blueboard_macro_handler.client.sys.platform` to `linux` |
| A send error is followed by reopen | Treat it as recovery evidence, not a diagnosis of cable, driver, ownership, or amplifier cause |

## Operational stop conditions

Stop live testing and restore the baseline if the wrong model/application is in
use, a port choice is ambiguous, observed state disagrees with a claimed
verification, a query produces malformed/checksum-invalid data, an effect cannot
be restored, cleanup leaves a port owned, or reconnect behavior becomes
unbounded. Record the failure honestly; do not relabel it as best-effort support.
